# Архитектура

## Два процесса

```
                    ┌──────────────────────┐
  VK Long Poll ───▶ │  bot (app.main)      │
                    │  команды, FSM /add   │
                    └──────────┬───────────┘
                               │ SQLAlchemy async
                    ┌──────────▼───────────┐
                    │  PostgreSQL 16       │
                    │  users, categories,  │
                    │  offers, snapshots,  │
                    │  subscriptions, ...  │
                    └──────────▲───────────┘
                               │ SQLAlchemy async
                    ┌──────────┴───────────┐
  funpay.com ◀───── │  worker (app.worker) │
                    │  APScheduler + parser│
                    └──────────┬───────────┘
                               │ VK API (messages.send)
                               ▼
                        пользователи VK
```

- **bot** принимает сообщения через Long Poll, ведёт диалог `/add`, показывает
  `/list` и `/stats`, загружает графики в VK.
- **worker** по расписанию парсит активные категории, пишет офферы и снапшоты,
  затем проверяет подписки и отправляет алерты.

Процессы не общаются напрямую: единственная точка синхронизации — PostgreSQL.
Это позволяет перезапускать их независимо и масштабировать воркер отдельно.

## Почему без API и сайта

MVP не принимает входящие HTTP-запросы:

- Long Poll не требует публичного домена и TLS;
- нет поверхности атаки на API;
- проще развернуть на ноутбуке или дешёвом VPS.

Парсер ходит только на публичные страницы FunPay, поэтому исходящих соединений
достаточно.

## Слои

| Слой | Модули | Ответственность |
|---|---|---|
| Транспорт | `app/bot`, `app/main.py` | VK, команды, клавиатуры, FSM |
| Планировщик | `app/worker.py` | расписание, жизненный цикл |
| Сервисы | `app/services` | мониторинг, алерты, графики, загрузка фото |
| Хранилище | `app/db` | модели SQLAlchemy, репозитории, сессии |
| Источники | `app/parsers` | `BaseParser`, `FunPayParser` |

`BaseParser` отделяет источник данных от остальных слоёв. Второй парсер (например,
Steam) добавляется реализацией интерфейса без изменений в БД и боте.

## Поток данных

1. Пользователь добавляет подписку через бота.
2. Воркер вызывает `MonitoringService.run_all_active()`.
3. `FunPayParser` скачивает и разбирает страницу категории.
4. Репозитории обновляют офферы и пишут снапшоты min/median/count по серверам.
5. `AlertService` проверяет активные подписки этой категории.
6. Успешные уведомления отправляются в VK и записываются в `notifications`.

## Обработка ошибок

- Ошибка парсинга не останавливает воркер: она попадает в `parse_runs`.
- Ошибка отправки алерта логируется; запись в `notifications` не создаётся,
  поэтому следующая попытка возможна сразу.
- Если график не загрузился, текст уведомления всё равно отправляется.
- Если `VK_GROUP_TOKEN` пуст, воркер продолжает парсинг без алертов.
