# Воркер

`python -m app.worker` запускает APScheduler. Первый прогон выполняется сразу,
следующие — каждые `PARSE_INTERVAL_MINUTES` с jitter ±2 минуты.

## Один прогон категории

1. В `parse_runs` создаётся запись со статусом `running`.
2. `FunPayParser` скачивает и разбирает страницу.
3. В одной транзакции:
   - создаются недостающие серверы;
   - таблица `offers` категории заменяется свежими офферами;
   - по каждому серверу пишется снапшот min/median/count;
   - `last_parsed_at` категории обновляется;
   - запуск закрывается статусом `ok` или `error`.
4. Если категория разобрана успешно, `AlertService` проверяет подписки.

## Ошибки

- исключение парсера записывается в `parse_runs.error_text`;
- воркер переходит к следующей категории;
- если БД недоступна при записи ошибки, это логируется, но процесс не падает;
- при старте воркер помечает зависшие запуски (`running` старше часа) как
  `error`, чтобы `/status` не показывал вечный прогресс.

## Планировщик

```python
scheduler.add_job(
    parse_job,
    "interval",
    minutes=settings.parse_interval_minutes,
    jitter=120,
    max_instances=1,
    coalesce=True,
)
```

`max_instances=1` и `coalesce=True` не дают запускам накладываться друг на друга,
если предыдущий прогон затянулся.

## Остановка

SIGINT/SIGTERM останавливают планировщик, закрывают HTTP-клиент парсера,
VK-клиент и пул соединений БД. В Docker Compose это происходит при `docker compose
down` и перезапуске контейнера.

## Ручной прогон

```bash
python -m app.worker                    # обычный режим
python scripts/parse_once.py /chips/30/ # только парсер, без БД
```

Админ может перепарсить категорию из бота: `/reparse 3` или
`/reparse /chips/30/`.
