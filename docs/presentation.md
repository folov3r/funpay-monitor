# Презентация и демо

Каркас на 12 слайдов. Текст можно сокращать под регламент защиты.

## 1. Титул

- FunPay Monitor — настольное приложение для мониторинга цен на игровом
  маркетплейсе FunPay.
- Дипломный проект, команда из 4 человек.
- Роли: код, документация, презентация, QA.

## 2. Проблема

- Цены на FunPay меняются в течение дня.
- Дешёвые лоты выкупают быстро, вручную уследить за десятками категорий сложно.
- Готовые сервисы требуют регистрации, установки или платной подписки.

## 3. Цель и задачи

**Цель:** приложение, которое само следит за ценой и присылает уведомление,
когда товар дешевеет.

Задачи:

1. Разобрать страницы FunPay `/chips/` и `/lots/`.
2. Фильтровать предложения по типу, названию и серверу.
3. Хранить историю цен локально в SQLite.
4. Дать пользователю подписки с тремя режимами алертов.
5. Показывать графики и присылать системные уведомления.
6. Собрать установщики для Windows и Linux, обеспечить тесты и CI.

## 4. Почему настольное приложение

- Работает без собственного сервера и регистрации.
- Данные остаются на компьютере пользователя.
- История и графики доступны без интернета.
- Один интерфейс открывается и в окне, и в браузере.
- VK-бот остаётся дополнительным каналом, но не обязателен.

## 5. Архитектура

Слайд со схемой из `desktop.md`:

- окно Tauri (Rust) — рамка, трей, запуск ядра;
- Python-ядро (FastAPI) — парсер, планировщик, алерты, локальный API;
- SQLite — категории, предложения, история, подписки, журнал;
- React-фронтенд — один и тот же в окне и в браузере;
- FunPay — источник данных.

Отметить: API слушает только `127.0.0.1`, наружу ничего не открыто.

## 6. Модель данных

Восемь таблиц:

`users`, `categories`, `servers`, `offers`, `price_snapshots`, `parse_runs`,
`subscriptions`, `notifications`.

Показать ER-диаграмму из `data-model.md`. Подчеркнуть:

- `offers` — текущее состояние;
- `price_snapshots` — история min/median/count;
- `notifications` — журнал и кулдаун;
- деньги хранятся в микро-рублях целыми числами, чтобы не терять точность.

## 7. Парсинг FunPay

- `a.tc-item`, `.tc-price`, `.tc-amount`, `data-server`.
- Тип — `data-f-type`, способ — `data-f-method`, название — `.tc-desc-text`.
- Подпись поля выбора берётся со страницы: «Сервер» или «Способ передачи».
- Точная цена из `data-s`, если она согласуется с видимой.
- Количество `кк` нормализуется в миллионы.
- JSON-LD `lowPrice` не совпал с таблицей — источник истины таблица.
- HTML-фикстуры в тестах защищают от смены вёрстки.
- Большая страница разбирается в отдельном потоке, чтобы не тормозить ядро.
- Пауза 3 с, backoff на 429/5xx, интервал 15 минут.

## 8. Логика алертов

| Режим | Условие |
|---|---|
| `abs` | цена ниже порога |
| `pct` | падение на N% к прошлому снапшоту |
| `lowest` | новый исторический минимум |

- Кулдаун 6 часов на подписку.
- Журнал `notifications` переживает перезапуск.
- Системное уведомление Windows или Linux плюс запись в журнале приложения.
- В VK-канале к сообщению прикрепляется график.

## 9. Демо

Сценарий:

1. Запуск приложения: окно открывается, ядро стартует само.
2. Вкладка «Категории», ссылка `https://funpay.com/chips/99/` — подпись
   «Способ передачи», сводка цен и график.
3. Ссылка `https://funpay.com/lots/2932/` — тип «Предметы», поиск
   `cosmic relic`, сводка min/медиана/количество и три самых дешёвых лота.
4. Вкладка «Подписки»: выбор сервера, режима и порога; сохранение.
5. «Уведомления» — журнал срабатываний, «Состояние» — последние прогоны.
6. Открыть `http://127.0.0.1:8765` в браузере — тот же интерфейс.
7. Перепарсинг или искусственное снижение порога → системное уведомление.
8. Закрыть окно в трей и открыть снова; перезапуск сохраняет данные.

Записать видео заранее на случай проблем с сетью.

## 10. Тестирование и CI

- 221 тест: 192 unit без внешней базы и 29 интеграционных на PostgreSQL 16.
- Парсер проверяется на сохранённых HTML-фикстурах.
- Проверены `ruff check`, `ruff format --check` и `mkdocs build --strict`.
- GitHub Actions: миграции, ruff, pytest, docker build, сборка фронтенда.
- Релизный workflow по тегу `v*` собирает установщики Windows и Linux.
- Все коммиты проходят CI.

## 11. Результаты и метрики

- 8 таблиц, 2 процесса (окно и ядро), 1 файл базы.
- На тестовой категории `/lots/2932/` парсер находит около 3000 офферов.
- Фильтр по типу и названию позволяет следить за конкретным предметом.
- Сразу после выбора фильтра видно количество, минимум, медиану и три самых
  дешёвых лота — без среднего, которое искажают лоты-пачки.
- Хранится история min/median/count по каждому серверу и срезу.
- Алерты не дублируются благодаря кулдауну.
- Размер Python-ядра — около 42 МБ, окно использует системный WebView.
- Установщик собирается одной командой, сборка автоматизирована.

## 12. Ограничения и развитие

Ограничения:

- только FunPay, без второго источника;
- один экземпляр приложения на порт `8765`;
- нет автоматических обновлений и бэкапов;
- установщик собирается только под текущую ОС;
- системное уведомление содержит текст без графика.

Развитие:

- парсер Steam через `BaseParser`;
- аналитика продавцов и серверов;
- очередь уведомлений;
- автозапуск, бэкапы и автообновления;
- подключение VK-бота как дополнительного канала.

## Вопросы, к которым стоит подготовиться

- Почему не Electron? — Tauri использует системный WebView: меньше памяти и
  размер установщика.
- Почему ядро на Python, а не на Rust? — парсер и логика уже были готовы, а
  срок 3–4 недели не позволял безопасно переписать всё на новом языке.
- Почему не API FunPay? — публичного API нет, только страницы.
- Что будет при смене вёрстки? — тесты на фикстурах и статус `error` в
  `parse_runs`.
- Как не забанили? — паузы, backoff, редкий интервал, публичные страницы.
- Почему SQLite? — один пользователь, один компьютер, не нужен сервер и
  настройка; вся история в одном файле.
- Почему медиана, а не среднее? — лоты-пачки сильно завышают среднее.
- Что с безопасностью? — API слушает только loopback, данные не покидают
  компьютер, токен VK не требуется.
- Почему два интерфейса? — один React-фронтенд: окно Tauri и браузер, не нужно
  поддерживать две версии.
