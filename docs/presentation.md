# Презентация и демо

Каркас на 12 слайдов. Текст можно сокращать под регламент защиты.

## 1. Титул

- FunPay Monitor — VK-бот мониторинга цен на игровом маркетплейсе.
- Дипломный проект, команда из 4 человек.
- Роли: код, документация, презентация, QA.

## 2. Проблема

- Цены на FunPay меняются в течение дня.
- Дешёвые лоты выкупают быстро, вручную уследить за десятками категорий сложно.
- Готовые сервисы требуют установки или платной подписки.

## 3. Цель и задачи

**Цель:** бот, который сам следит за ценой и присылает уведомление в VK.

Задачи:

1. Разобрать страницы FunPay `/chips/` и `/lots/`.
2. Хранить историю цен в PostgreSQL.
3. Дать пользователю подписки с тремя режимами алертов.
4. Отправлять уведомления с графиком.
5. Обеспечить тесты, CI и запуск через Docker Compose.

## 4. Почему VK-бот

- Аудитория FunPay и VK пересекается.
- Уведомление приходит в привычное приложение.
- Ничего не нужно устанавливать.
- Long Poll не требует публичного домена и HTTPS.

## 5. Архитектура

Слайд со схемой из `architecture.md`:

- `bot` — команды и FSM `/add`;
- `worker` — APScheduler и парсер;
- PostgreSQL — единственная точка обмена;
- FunPay — источник данных;
- VK API — доставка сообщений.

Отметить: сайта и входящего API нет, только исходящие соединения.

## 6. Модель данных

Восемь таблиц:

`users`, `categories`, `servers`, `offers`, `price_snapshots`, `parse_runs`,
`subscriptions`, `notifications`.

Показать ER-диаграмму из `data-model.md`. Подчеркнуть:

- `offers` — текущее состояние;
- `price_snapshots` — история min/median/count;
- `notifications` — журнал и кулдаун.

## 7. Парсинг FunPay

- `a.tc-item`, `.tc-price`, `.tc-amount`, `data-server`.
- Количество `кк` нормализуется в миллионы.
- JSON-LD `lowPrice` не совпал с таблицей — источник истины таблица.
- HTML-фикстуры в тестах защищают от смены вёрстки.
- Пауза 3 с, backoff на 429/5xx, интервал 15 минут.

## 8. Логика алертов

| Режим | Условие |
|---|---|
| `abs` | цена ниже порога |
| `pct` | падение на N% к прошлому снапшоту |
| `lowest` | новый исторический минимум |

- Кулдаун 6 часов на подписку.
- Журнал `notifications` переживает перезапуск.
- График прикрепляется к сообщению; при ошибке загрузки уходит текст.

## 9. Демо

Сценарий:

1. `/start` и главное меню.
2. `/add https://funpay.com/chips/30/`.
3. Выбор сервера, режима и порога.
4. `/list` — подписка и текущая цена.
5. `/stats 1` — график за 7 дней.
6. `/reparse` или искусственное снижение порога → алерт.
7. `/status` — сводка для админа.

Записать видео заранее на случай проблем с сетью.

## 10. Тестирование и CI

- 156 тестов: unit + интеграционные на PostgreSQL 16.
- Парсер проверяется на сохранённых HTML-фикстурах.
- GitHub Actions: миграции, ruff, pytest, docker build.
- Все коммиты проходят CI.

## 11. Результаты и метрики

- 8 таблиц, 2 процесса, 6 команд пользователя и 2 админские.
- На тестовой категории `/chips/30/` парсер находит около 292 офферов.
- Хранится история min/median/count по каждому серверу.
- Алерты не дублируются благодаря кулдауну.
- Запуск одной командой `docker compose up --build -d`.

## 12. Ограничения и развитие

Ограничения:

- только FunPay, без второго источника;
- один экземпляр воркера;
- состояние `/add` не переживает перезапуск;
- нет автоматических бэкапов.

Развитие:

- парсер Steam через `BaseParser`;
- аналитика продавцов и серверов;
- очередь уведомлений;
- мониторинг и бэкапы;
- опционально VK ID OAuth.

## Вопросы, к которым стоит подготовиться

- Почему не Telegram? — требование использовать VK, аудитория и привычный канал.
- Почему не API FunPay? — публичного API нет, только страницы.
- Что будет при смене вёрстки? — тесты на фикстурах и статус `error` в `parse_runs`.
- Как не забанили? — паузы, backoff, редкий интервал, публичные страницы.
- Почему PostgreSQL? — история, агрегаты, транзакции, знакомый стек.
- Почему два процесса? — парсинг не блокирует ответы бота, независимый перезапуск.
